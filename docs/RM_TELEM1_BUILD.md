# БУСА-1М №001 — RainMaker TELEM1, 2026-11-05

Версия: `14v9-N16R8-RM-TELEM1-20261105`. База — ровно BLE FIX3
`46baec115f91e2637c2adf493e9449093700c9d1`. Отдельная ветка
`fix/busa-rainmaker-telemetry-20261105`. Реальное оборудование не прошивалось.

## Установленный дефект и границы вывода

В FIX3 `busaRainMakerPoll()` каждые 2,5 секунды повторно публиковал настройки
по одному параметру, даже когда настройки не менялись. Температуры и время
работы отправлялись после этих публикаций, только каждые 30 секунд.
Каждый `updateAndReportParam()` создаёт отдельную публикацию.

В **поставляемом ESP32 Arduino 2.0.17 SDK для ESP32-S3 qio_opi** включён
`CONFIG_ESP_RMAKER_MQTT_ENABLE_BUDGETING`: начальный бюджет 100, восстановление
одного сообщения каждые 5 секунд (12/мин). Прежний поток неизменных настроек
превышал этот бюджет многократно и мог отнимать восстановленные токены у
температур/времени работы при остающемся подключённым MQTT.

Дополнительно проверен машинный код поставляемых `libesp_rainmaker.a` и
`librmaker_common.a`: результат MQTT-публикации не передаётся вызывающему
`esp_rmaker_param_update_and_report`; успешное обновление модели может вернуть
ESP_OK при неудаче транспорта. Приложение FIX3 игнорировало и этот результат.
Дизассемблирование проверялось для установленного SDK, а не только исходников
последней версии Espressif. См. `RM_TELEM1_SDK_EVIDENCE.txt`.

Регрессионный тест исполняет **неизменённую функцию FIX3** с моделью этих
ограничений SDK: за 600 секунд моделирования — 1521 отброшенная публикация,
последнее доставленное время работы 30 секунд. Это воспроизведение механизма
ошибки в коде, **не замер настоящего ESP32** и не объяснение именно числа 265
в журнале владельца. Фактические MQTT-журналы неисправного устройства отсутствуют.

## Исправления

* Один пакет со всеми обновлёнными параметрами через официальный пакетный API:
  локальные `esp_rmaker_param_update`, затем один `update_and_report` существующего
  параметра «Работает секунд». Целевой интервал — 10 секунд (6 сообщений/мин).
* Все четыре действительных температуры отправляются регулярно, даже если они
  не изменились. При отсутствии/NaN передаётся статус отключённого датчика;
  новое вымышленное значение 0 °C не создаётся.
* Неизменные настройки не обновляются повторно. После изменения настройки,
  переподключения, ошибки транспорта или неопределённого ACK выполняется
  повторная синхронизация фактических локальных значений.
* Главный цикл только формирует один ограниченный снимок. Публикация выполняется
  официальной RainMaker work queue; постановка без ожидания, накопления снимков
  нет. Снимок старше 20 секунд отбрасывается. OTA/сканирование приостанавливают
  новую отправку; цикл Google не блокирует постановку снимка.
* Сохранены штатный транспорт, TLS, авторизация, MQTT-бюджет и переподключение
  Espressif. Нет дополнительных Wi-Fi disconnect/restart/provision/reset NVS.
* Диагностика разделяет обновление SDK-модели, передачу транспорту и получение
  PUBACK брокера по **точному message ID нашего пакета**. Чужие MQTT-события не
  засчитываются. Учтён ACK до возврата publish, нарушенный порядок ACK, timeout,
  удаление сообщения, отключение и ограниченная память. ACK брокера **не является
  подтверждением обновления экрана/базы приложения RainMaker**.

`GET http://192.168.4.1/api/rainmaker/status`, объект `telemetry`:
`mqtt_connected`, `init_rc`, `report_calls`, `report_api_ok`, `last_report_rc`,
`last_transport_rc`, `api_without_transport`, `transport_failures`,
`batch_enqueued`, `broker_confirmed_batches`, `last_broker_ack_uptime_s`,
`pending_acks`, `unconfirmed_batches`, `queue_failures`, `budget_deferrals`,
`snapshot_temperatures`. `cloud_app_delivery` честно остаётся `not_observed`.
Истечение ACK через 60 секунд означает неопределённость, а не доказанную потерю.

## Неизменность утверждённых функций

Автоматический побайтовый контракт сравнивает с FIX3 все прежние отдельные
исходники датчиков/звука/Google/клавиатуры/экрана/BLE recovery/OTA boot и CSV
разделов. В BUSA_Main.h разрешены только строка версии и дополнение существующего
диагностического JSON. Исходный код создания RainMaker node/devices/parameters
совпадает целиком, кроме установки наблюдателя транспорта перед RMaker.start.
Имена, типы, права параметров и обработка команд владельца не менялись.
Распиновка, исполнительные действия и локальный веб-интерфейс сохранены.
Проверка исходников подтверждает отсутствие новых операций очистки NVS/fctry,
но не заменяет испытания сохранения данных на устройстве.

## Автоматические проверки

```
python3 -B tests/test_ble_ota.py
python3 -B tests/test_rm_tracker.py
python3 -B tests/test_rm_telemetry.py
python3 -B tests/test_rm_preservation.py
python3 -B -m unittest discover -s tests -p test_firmware_contract.py -v
```

Исполняются настоящие C++ функции прошивки с детерминированными моделями SDK,
не имитация проверки живого ESP32. Часовой тест: 360 пакетов без бюджетных
отказов; T3 24,81 → 29,69; статические настройки не переотправляются.
Проверяются API ESP_OK без транспорта, транспортный отказ, переполнение очереди,
потеря/возврат MQTT, OTA/scan pause, invalid sensor, устаревший снимок,
недостаток бюджета и посторонний PUBACK. Отдельно ACK-гонки и rollover.
Существующие BLE/OTA/credential regression и 4 contract unit tests сохранены.
Встроенный JS BUSA_Main.h и index.html проверяется `node --check`.

## Сборка

Точные команды доступны в `.github/workflows/busa-rm-telemetry.yml`.
Arduino CLI, официальный неизменённый ESP32 core **2.0.17**; библиотеки:
BusIO 1.17.4, OneWire 2.3.8, DallasTemperature 4.0.6, GFX 1.13.0,
ST7735/ST7789 1.12.0, ILI9341 1.7.0, U8g2_for_Adafruit_GFX 1.8.0.

```
python3 ci/generate_google_ca.py --output firmware/BUSA_1M_WIFI_3v_GOOGLE/BUSA_GoogleCA.h
arduino-cli compile --clean --fqbn 'esp32:esp32:esp32s3:FlashSize=16M,PartitionScheme=app3M_fat9M_16MB,PSRAM=opi,CDCOnBoot=cdc,USBMode=hwcdc,FlashMode=qio,DebugLevel=none' --output-dir out firmware/BUSA_1M_WIFI_3v_GOOGLE
python3 ci/package_rm_telemetry.py --build-dir out --core-dir /path/to/esp32/2.0.17 --esptool /path/to/esptool_py/4.5.1/esptool.py
```

Подготовительный скрипт проверяет отпечатки Google CA. Остальные BLE-скрипты
только проверяют исходники, не применяют скрытых исправлений. ZIP включает
полный собираемый скетч, заголовки, CSV, CI, тесты/fixtures и эту инструкцию;
старый вложенный архив .ino.zip исключён. SOURCE_COMMIT фиксирует ревизию.

Проверяются ESP32-S3 chip ID 9, APP descriptor, встроенная версия, image checksum,
validation hash, размер APP ≤ 0x300000, побайтовое вхождение APP в USB,
идентичность bootloader/partition table/boot_app0, SHA-256 двух BIN.
Разметка FIX3: app0 0x10000/3MiB, app1 0x310000/3MiB;
nvs 0x9000/0x5000; otadata 0xe000/0x2000; RainMaker fctry 0x610000/0x6000.
Настройка меню QIO использует официальный ROM-заголовок DIO; merge оставляет
заголовки `keep`, не переписывает их на qio. Flash 16MB, PSRAM OPI 8MB.

## Установка и iPhone

Предпочтительно **OTA BIN** через существующее локальное приложение БУСА:
сохранить файл в «Файлы» iPhone, подключиться к BUSA-1M-001-R04, открыть
192.168.4.1 и выбрать APP BIN в штатном OTA. Не выбирать USB MERGED как APP.
При совпадающей с FIX3 разметке OTA меняет только слот приложения: NVS,
Wi-Fi и fctry-регистрация RainMaker сохраняются по конструкции. Не нажимать
сброс настроек и не запускать повторное BLE-сопряжение. Физически это ещё
не подтверждено новой прошивкой.

**USB MERGED** записывается с адреса 0x0 на ESP32-S3 N16R8 с указанной разметкой.
Это компактный образ, не дамп 16MB. Его заполнение промежутков затрагивает
обычный NVS и otadata: USB не обещает сохранить локальные настройки/Wi-Fi.
Перед USB нужна резервная копия устройства. Образ заканчивается до fctry,
но **erase-all запрещён**, если нужно сохранить регистрацию RainMaker.
Для обновления действующего зарегистрированного устройства использовать OTA.
Никакая команда прошивки реального устройства в этой работе не выполнялась.

Готовые файлы публикуются отдельно в постоянном разделе `releases/artifacts`
репозитория; прямые HTTPS raw-ссылки закрепляются за коммитом. Их содержимое
повторно скачивается и сверяется по SHA-256, временная ссылка ChatGPT не нужна.

## Обязательные оставшиеся физические испытания

1. Сохранить начальный `/api/rainmaker/status`; после OTA без BLE убедиться в
   восстановлении MQTT и росте broker_confirmed_batches каждые ~10 секунд.
2. Проверить T1–T4 и «Работает секунд» **в реальном RainMaker на iPhone**,
   сопоставить снимки Google и local status, изменить температуру T3.
3. Отключить Интернет, сохранив AP: экран/клавиатура/звук/датчики/локальное
   приложение продолжают работу; после возврата Интернета MQTT и телеметрия
   восстанавливаются без регистрации. Проверить Wi-Fi AP+STA одновременно.
4. Перезапуск питания и RESET: та же RainMaker identity, Wi-Fi/настройки/NVS;
   отдельное повторное OTA, проверка слотов и отсутствия отката.
5. Длительная проверка TLS/MQTT, памяти/стека SDK work queue, watchdog,
   задержек и потерь сети; реальная серверная доставка и отображение в iPhone.

Эти испытания **не проведены**: физического ESP32, iPhone и доступа к облаку
владельца нет. Успешная сборка/модель/PUBACK не объявляются доказательством
сквозной доставки до приложения. Наблюдаемая ошибка имеет доказанный
программный механизм и исправление; окончательное подтверждение — пункты выше.
