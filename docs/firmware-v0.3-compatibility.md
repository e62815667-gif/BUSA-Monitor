# Совместимость БУСА-Монитор ↔ БУСА-1М №001 v0.3

**Проверено по исходному коду** `BUSA_1M_001.ino` из архива `BUSA-1M-001-firmware-v0.3-monitor.zip`. Это контрактные тесты без платы, не испытания оборудования.

- Wi-Fi AP: `BUSA-1M-001`, IP `192.168.4.1` (пароль из прошивки необходимо сменить до регулярной эксплуатации).
- `GET /monitor`: локальная страница мониторинга, размещённая непосредственно на ESP32-S3. Не зависит от GitHub Pages.
- `GET /api/status`: JSON с `device`, `mode`, `volume_l`, `level_mm`, `temperature_count`, `temperatures`.
- `temperatures`: **ровно четыре** элемента; `channel` 1–4, `name`, `ok`, `celsius` (число при `ok=true`, иначе `null`), `address`.
- `POST /api/volume`: `application/x-www-form-urlencoded`, параметр `liters` от 0 до 100; ответ `ok` и `volume_l`. Это **ручной справочный ввод**, не физический датчик уровня.
- `level_mm=volume_l*8` — расчётный показатель только профиля №001; нельзя трактовать как фактический уровень.
- Аварийная остановка и исполнительные команды в прошивке **отсутствуют**. Приложение не должно показывать их как действующие.
- HTTPS GitHub Pages не может напрямую и надёжно обращаться к HTTP `192.168.4.1`; для реальных данных используется локальный `/monitor`.

## Проверка без оборудования
В каталоге `tests/` лежат два образца ответов API и Python-тесты контракта. Команда:
```
python -m unittest discover -s tests -v
```
Тесты проверяют структуру JSON, четыре температуры, отсутствие данных, диапазоны и расчётный показатель уровня. Они не компилируют прошивку и не проверяют Wi-Fi или датчики.

## До подключения платы
Нужны компиляция для конкретной ESP32-S3, проверка адресов датчиков DS18B20, проверка HTTP-ответов на устройстве и испытания отказов. Физический L01 реализовать отдельно после выбора модели. Схему аппаратного аварийного отключения разрабатывать и проверять независимо.
